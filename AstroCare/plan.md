# AstroCare Mission Health Console — Implementation Plan

## Product scope

Build a polished, presentation-ready, working AstroCare Astronaut Health Monitoring & Spaceflight Countermeasure System based on the attached AstroCare AI Execution Prompts. Preserve its product features while replacing Java/Spring with a React client and a Node.js backend, as the user authorized. The result is a full-stack application, not a frontend-only mockup.

Flight Surgeons have multi-astronaut oversight, simulator controls, and anatomical marker pinning. Astronauts have a personal telemetry cockpit and emergency SOS access. The website includes a secure-style role login portal, indexed synthetic crew roster, live vital cards, an expanding historical chart for each metric, a multi-axis real-time telemetry chart, a distinct ECG Lead II waveform, a clickable SVG anatomy map with severity highlights, notes and marker persistence, an in-app SOS event flow, a Dark/Light toggle, and an Export Clinical PDF action.

The backend uses authenticated role checks and persistent MySQL records. It implements `POST /api/auth/login`, `GET /api/astronauts`, `GET /api/health/latest/{astronautId}`, `GET /api/health/history/{astronautId}`, `POST /api/demo/simulate` with `NORMAL`, `WARNING`, `CRITICAL`, and `EVA_STRAIN`, `GET` and `POST /api/anatomy/markers`, `POST /api/emergency/sos`, and `GET /api/reports/pdf/{astronautId}`. It also exposes a two-second telemetry stream at `/topic/telemetry/{astronautId}` using authenticated WebSockets and JSON updates. Database tables are `Users`, `Roles` (`ROLE_FLIGHT_SURGEON`, `ROLE_ASTRONAUT`), `User_Roles`, `Astronauts`, `Mission_Details`, `Vital_Signs`, `Anatomical_Markers`, `Health_Alerts`, `Emergency_Events`, `Medical_History`, and `Notifications`. Vital records include heart rate, SpO2, systolic and diastolic blood pressure, core temperature, respiratory rate, ECG Lead II waveform arrays, EVA suit pressure in PSI, and ionizing radiation in mSv/h. Schemas are normalized and indexed; migrations and seed records are idempotent. Demo account passwords are BCrypt-hashed.

Every two seconds, a server scheduler generates and persists changing physiological/suit-environment readings, evaluates thresholds, records alerts, and broadcasts current readings. The rule engine flags SANS/cephalic fluid-shift patterns, hypoxia, decompression risk from EVA suit pressure drops, radiation spikes, and thermal stress; each rule can identify an affected anatomy zone that the interface illuminates. The simulator modes drive coherent metrics, alerts, and anatomy highlights rather than static examples.

## Scientific provenance and safety boundary

The attached brief asks for NASA OSDR-calibrated telemetry, but the official OSDR Inspiration4 overview primarily lists processed biological samples and notes that private raw data require an application and board approval. A peer-reviewed study reports selected-period Apple Watch heart rate, heart-rate variability, and blood oxygen saturation, with mission-phase variability; these sources do not provide a validated continuous dataset for all requested fields such as EVA pressure, radiation rate, core temperature, systolic/diastolic blood pressure, respiratory rate, and ECG Lead II. The application will therefore use synthetic demo crew and telemetry, not real or personally attributable Inspiration4 records. Rules and thresholds will be clearly labeled configurable demonstration values, and alerts as rule-engine flags rather than diagnoses. The app will not claim regulatory validation or contact real flight control. Source details are recorded in `OSDR-NOTES.md` and surfaced in the README.

## Implementation and architecture

Use React + TypeScript + Vite for the client and Node.js + Express + TypeScript for the API. A single Node process serves the client and REST endpoints from the same origin on the configured project port. Use `mysql2` with committed SQL migrations and indexed relational tables, `bcryptjs` for password hashing, signed JWT-backed application sessions in an HttpOnly cookie, Express role middleware, `ws` with STOMP-compatible topic frames, Chart.js for plots, and PDFKit for server-side clinical PDFs. The explicit username/password login and seed accounts follow the attached prompt; the application will use its own cookie name, never the platform-owned `app_session_id`. For HTTPS Preview, application cookies use `SameSite=None; Secure` to remain eligible in the embedded Preview context.

The Flight Surgeon seeded account can view the crew, choose crew members, set a simulation scenario, and add/resolve anatomical markers. The Astronaut seeded account is restricted to its own profile and readings; it can submit an SOS, which creates a persisted emergency event and notification visible to the flight-surgeon console. It is an in-app demo workflow, not an external emergency call. The report API applies the same role-based data visibility before returning a generated PDF.

An authenticated WebSocket connection subscribes to authorized `/topic/telemetry/{astronautId}` topics. The Node implementation preserves the topic/update behavior in the prompt while using a React-compatible Node WebSocket service rather than the Spring STOMP stack. A singleton database advisory lock prevents duplicate telemetry schedulers when more than one app process is active. Each browser view consumes the same API and event stream so the selected crew member, metrics, charts, alert feed, and anatomy remain consistent.

## Project structure

- `client/src/` contains the React TypeScript dashboard, login portal, role views, reusable telemetry cards, chart panels, crew roster, alert rail, simulator controls, clickable SVG anatomy, API client, authentication state, and WebSocket client.
- `client/public/manus-routes.json` declares the actual single-page route manifest; `client/public/` contains site metadata and icon assets.
- `server/src/index.ts` starts the HTTP application, runs migrations/seeds, coordinates the telemetry scheduler, and exposes readiness; `server/src/app.ts` configures Express and serves Vite middleware during development or built assets in production.
- `server/src/controllers/` implements the named REST route families. `server/src/services/` owns telemetry generation, configurable physiology rules, alert and notification creation, SOS handling, and clinical PDF rendering.
- `server/src/repositories/` provides SQL access; `server/src/auth/` handles bcrypt login, signed session cookies, authentication, and role authorization; `server/src/db/` contains the connection pool, versioned SQL migrations, migration history, and idempotent seed data; `server/src/realtime/` implements authenticated WebSocket topic subscriptions and broadcasts.
- Root `README.md` documents startup, demo credentials, available API/WebSocket behaviors, storage, threshold provenance, and the requested three-minute hackathon demo script. `plan.md`, `TODO.md`, and `OSDR-NOTES.md` track the approved scope, outcomes, and NASA source constraints.

## Design direction

The attached frontend prompt explicitly specifies a dark Obsidian & Electric Teal glassmorphic theme, a Dark/Light theme toggle, blurred panels, fine translucent borders, and JetBrains Mono tabular telemetry. The site will follow that direction directly.

**Design movement:** contemporary mission-control glassmorphism, restrained by clinical instrumentation conventions. **Core principles:** readings remain scannable; severity is encoded by color and text/icon, never color alone; crew context stays close to telemetry; actions return immediate, legible feedback. **Color philosophy:** deep Obsidian surfaces keep attention on instrument values; Electric Teal signals AstroCare and healthy streaming; amber, orange, and red communicate escalating rule-engine attention; the light theme preserves those same severity meanings. **Layout paradigm:** asymmetric command workspace with a compact navigation rail, crew selector, wide telemetry field, and right-side clinical context/alert rail; anatomy and history occupy focused panels. **Signature elements:** orbital-cyan focus rules, tabular monospaced telemetry, and a wireframe body map with severity-coded markers. **Interaction philosophy:** selecting a crew member synchronizes the full dashboard; clicking a vital reveals history; selecting an anatomical zone saves a marker/note; scenarios and SOS create explicit, auditable state changes. **Animation:** subtle telemetry motion and restrained transitions, with reduced-motion support. **Typography:** Space Grotesk for interface/headings and JetBrains Mono for telemetry, timestamps, and IDs. **Brand essence:** a flight-medicine console for crew health oversight in spaceflight; precise, vigilant, composed. **Brand voice:** concise operational language, such as “Telemetry stream active” and “Marker saved to the medical record.” **Wordmark:** a custom AstroCare wordmark paired with an orbit-and-pulse glyph drawn in SVG. **Signature brand color:** Electric Teal `#25E0CF`.

## Serving, managed resources, and constraints

The application requires the managed server and managed MySQL database. Enabling either is a one-way change that cannot be turned off later; development and publication use the same database, so migrations and seed data are durable changes to that shared store. These resources will only be enabled after approval of this plan. The application reads `DATABASE_URL` at runtime; production builds must not depend on the DSN. Use a pinned npm toolchain and lockfile. Keep migrations deterministic and additive where possible, and preserve demo record edits on restart by using migration history and idempotent seed inserts. The production container builds the Vite client and runs the API server; the dev process serves both through the configured runtime port. The project does not enable Redis or require external provider credentials.
